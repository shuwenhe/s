## Question 2: What information does bin/s_seed save after import?

### Answer:

**Current import processing (seed/semantic/analyzer.c lines 1510-1540):**

```c
// When import ("std.io") is processed:

1. Extract module root: "std" from "std.io"

2. Register symbol "std":
   scope_define(ctx->current_scope,
       "std",           // symbol name
       SYMBOL_IMPORT,   // symbol kind
       0,               // param_count
       0,               // min_arity
       0,               // max_arity

       NULL,

3. Also load import signature:
   resolve_import_signature("std.io", &min_arity, &max_arity, &ret_type)

   scope_define(...,
       "std.io",        // or selector
       SYMBOL_IMPORT,
       0,
       min_arity,       // has arity info
       max_arity,
       ret_type,        // has return type
```

**What's available:**
- ✅ Symbol "std" exists with type "module"

- ✅ The signature includes arity and return type for functions
- ✅ Symbol "std.io" may be registered in scope

- ❌ When looking up member `eprintln` on `std.io`, no qualified name resolution exists

## Question 3: Can we find std.io + eprintln using existing information?

### Answer: YES, WITH BOUNDED CHANGES

**Current error path:**
```c
// analyze_expr for std.io.eprintln(...)

1. member->as.member_expr.object = "std.io"
2. analyze_expr(ctx, "std.io", &lhs_type) → lhs_type = ??? 
   (currently fails or returns "module")
3. Check if lhs_type has method "eprintln"
   → ERROR: type 'module' has no method 'eprintln'
```

**Proposed bounded fix:**

When analyzing member expression with qualified name:

```c
// In analyze_expr for AST_MEMBER_EXPR:

if (member->as.member_expr.object->kind == AST_MEMBER_EXPR) {
    // This is a CHAINED member: std.io.eprintln
    // Case: std.io.eprintln(...)
    
    char full_qualified_name[512];
    construct_qualified_name(member, full_qualified_name, sizeof(full_qualified_name));
    // Now full_qualified_name = "std.io.eprintln"
    
    // Look up in import_signatures
    // import_signatures contains entries for:
    //   "std.io.eprintln" → {arity: 1, return_type: "int"}
    
    signature_spec *sig = lookup_import_signature(full_qualified_name);
    if (sig) {
        *out_type = sig->return_type;
        // Mark this as resolved import call
        return 1;
    }
}
```

**Key insight:** The information is ALREADY THERE
- import_signatures has the full function path
- We just need to construct the qualified name and look it up
- No need to build a full module type system

## Question 4: Can this capability be frozen as bootstrap-only?

### Answer: YES

**What we're adding:**
```
Bounded Qualified Name Resolution (Bootstrap Context)
  = ability to match patterns like:
      std.io.eprintln
      std.io.eprint
      std.env.args
    against import_signatures metadata
    and resolve to function type
```

**Scope limits:**
- ✅ Only in bootstrap context (main.s)
- ✅ Only for imported functions with known signatures
- ✅ Only for patterns already in import_signatures.meta
- ✅ No runtime module type system needed
- ✅ No reflection or dynamic lookup
- ❌ Cannot add new import signatures at runtime
- ❌ Cannot discover methods dynamically
- ❌ Cannot access module fields

**Freezing mechanism:**
```c
// Add to bootstrap_subset.md or create bootstrap-qualified-names.md:

"Qualified name resolution applies only to:
 1. Identifiers matching pattern: pkg.sub.*.function
 2. Where pkg.sub.* is in the import_signatures.meta whitelist
 3. Function signatures are pre-computed and frozen
 4. This capability is used only during bootstrap compilation
 5. The canonical compiler does not rely on seed/semantic 
    for this feature"
```

**This is NOT:**
- ❌ Full B6.7.3 implementation
- ❌ Building a module type system in C
- ❌ Creating dual semantic authority
- ❌ Sharing resolver code with canonical compiler

**This IS:**
- ✅ A bootstrap-only lookup mechanism
- ✅ Using existing import_signatures metadata
- ✅ Localized to qualified member calls on imports
- ✅ Explicitly frozen to specific patterns
- ✅ Path A-lite

## Risk Assessment

### Path A-lite Risks: LOW
- ✅ Bounded to specific pattern (pkg.mod.func)
- ✅ Uses existing infrastructure (import_signatures)
- ✅ No new semantic model needed
- ✅ Explicitly scoped to bootstrap
- ✅ Can be frozen in contract
- ✅ No dual authority (just lookup in pre-computed table)

### Path B Risks: HIGH
- ❌ Full B6.7.3 implementation
- ❌ Module type system in C seed
- ❌ Potentially unbounded future growth
- ❌ Risk of becoming "second semantic authority"
- ❌ Synchronization with canonical compiler
- ❌ Hard to freeze or limit scope
