## Phase 2: Bootstrap Subset Contract Analysis

### What bootstrap-subset.md Explicitly Allows

```
unit       = "package" identifier function+ EOF
function   = "func" identifier "(" ")" "int" "{" "return" expression [";"] "}"
expression = decimal_integer | identifier "(" ")" | "(" expression ")"
```

**Features Explicitly Allowed:**
- Package declaration
- Function declarations (no parameters)
- Integer literals
- Function calls (no arguments)
- Parenthesized expressions
- Return statements

**Features Explicitly Denied in Doc:**
```
"Dotted names, imports, multiple files, package resolution, namespaces 
and visibility are outside this subset."
```

### What bootstrap_subset.c Actually Implements

From code inspection of `src/cmd/compile/stage0/bootstrap_subset.c`:

**Implemented:**
- `bs_skip_import_decl()`: Structurally skips import blocks (no semantic processing)
- `bs_local_binding()`: Handles `identifier := expression` with optional semicolon
- `bs_expression()`: Evaluates integers, local variables, function calls (no args)
- Variables: Local binding with assignment (not in original doc, but in implementation)

**Token Types Defined but Not Used:**
- `BS_STRING`: Tokenized but not evaluated
- `BS_DOT`: Tokenized but not evaluated (qualified names)

**Definitively Not Implemented:**
- String evaluation
- String concatenation
- Conditionals (if/else)
- Qualified member access
- Function parameters
- Any module/import semantic resolution

## Phase 3: Root0 (bin/s_seed) Current Capability

### What bin/s_seed Can Do

From empirical observation:
- ✓ Parse S source with imports
- ✓ Recognize package structure
- ✓ Parse function declarations
- ✓ Create AST nodes
- ✓ Register import symbols (type 'any')
- ✗ Resolve qualified member access
- ✗ Cannot type-check std.io as a package
- ✗ Cannot find method 'eprintln' on type 'any'

### Why std.io.eprintln Fails

```
Step 1: Parser reads "import "std.io"" → Creates import declaration ✓
Step 2: Semantic analyzer registers "std" → SYMBOL_IMPORT type ✓
Step 3: Parser reads "std.io" reference
Step 4: Semantic analyzer resolves "std" → finds symbol type 'any'
Step 5: Semantic analyzer tries to resolve ".io" member on 'any'
        → ERROR: type 'any' has no method 'eprintln'
```

Root0 cannot convert module symbol to actual package type with members.

### Gap Summary

**main.s requires Root0 to implement:**

2. String comparison and concatenation

- Control flow (if/else)
- Package resolution and qualified access
- Method dispatch on module types

**Total capability delta: 6+ major language features**

## Phase 5: Critical Determination

### The Real Question

> **Is main.s designed to be a bootstrap source that fits Root0's frozen capability?**

**Answer:** NO

**Evidence:**
1. main.s uses string parameters (Line 22: `string message`)
2. main.s uses string literals
3. main.s uses string comparison
4. main.s uses string concatenation
5. main.s uses conditionals
6. main.s uses qualified member access on imported modules

**None of these are in the bootstrap subset contract.**

## Phase 6: Decision Point

### Option A: Bounded Fix (Keep Ladder Design)

**Approach:** Modify main.s to fit bootstrap-subset contract

```s
// main.s REWRITTEN to use ONLY bootstrap capabilities:

package cmd

func main() int {
    return 0
}
```

**Outcome:** ✓ This compiles in bootstrap-subset
**Problem:** ✗ This is a useless compiler (does nothing)

**Reality:** Even the "simple" bootstrap source requires features outside the frozen contract.

### Option B: Ladder Design Problem (Current Path)

**Approach:** Extend Root0 to support features main.s needs

**What this requires:**
1. Add string type to Root0 type system
2. Add string literal parsing and evaluation
3. Add string comparison operators
4. Add string concatenation
5. Add if/else conditional
6. Add function parameter types
7. Add package/module type resolution
8. Add qualified member access and method dispatch

**Outcome:** Root0 becomes a production-grade semantic analyzer
**Problem:** ✗ This is no longer "bounded" — it's copying canonical compiler features into C seed

## Phase 7: Verification Against Frozen Constraints

### Previous Architectural Constraints

```
C-seed-qualified-resolution-extension = FORBIDDEN
    Rationale: Avoid dual semantic authority

permanent-dual-semantic-authority = FORBIDDEN
    Rationale: One compiler, one type system, one resolver
```

### Current Situation

If we implement qualified member resolution in Root0 to fix main.s:

```
Root0 semantic analyzer
├─ String type system
├─ String operations
├─ Conditional logic
├─ Module identity tracking
└─ Qualified member resolution
    └─ Method dispatch on package types

= Growing toward second semantic authority = VIOLATES CONSTRAINT
```

## Summary

### What We Discovered

| Aspect | Finding |
|--------|---------|
| first-broken-rung | Root0 → Stage1 (confirmed) |
| failure-layer | std.io.eprintln qualified call |
| root-cause | Module type resolution missing |
| type-of-gap | **NOT BOUNDED** |
| can-fix-with-frozen-capabilities | **NO** |
| requires-ladder-change | **YES** |

### What This Means

The bootstrap ladder as currently designed has a **structural problem**:

1. main.s is the bootstrap source
2. main.s requires features beyond bootstrap-subset contract
3. To fix Root0 → Stage1, must extend Root0 with these features
4. These features (string ops, conditionals, qualified resolution) are canonical compiler features
5. Implementing in Root0 violates the "no dual semantic authority" constraint

### The Real Fix Options

**Option A (Recommended):** Redesign bootstrap source
- Create a new bootstrap compiler source that fits bootstrap-subset contract
- Should do only absolute minimum: parse, compile to IR, emit assembler
- Use only integers, function calls, no strings, no conditionals, no qualified access

**Option B:** Accept Dual Authority (Relaxed Constraint)
- Extend Root0 to support needed features
- Acknowledge that Root0 has its own "bootstrap semantic authority"
- Separate from canonical authority, but both exist
- Requires explicit decision to relax earlier constraints

**Option C:** Different Bootstrap Strategy
- Use existing bootstrap ladder differently
- Or introduce intermediate stage that's simpler

---

## Recommendation

Before implementing any fix, **choose Option A or B explicitly**:

- **Option A:** Redesign bootstrap source (main.s → new_bootstrap.s)
  - Fits within frozen Root0 capabilities
  - Clean ladder boundary
  - More work upfront, but maintains architecture

- **Option B:** Extend Root0 semantic authority
  - Implement needed features in Root0
  - Acknowledge dual authority
  - Gets Stage1 faster, but muddies architecture

**Current assumption that "Root0 just needs B6.7.3 qualified resolver" is incorrect.**
Root0 needs: strings, conditionals, parameters, AND qualified resolver.

This is a **ladder design decision**, not a "B6.7.3 implementation" decision.
