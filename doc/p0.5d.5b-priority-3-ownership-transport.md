## Part B: Return Transport Mechanism

### Problem Statement

```
Source code:
  args := std.env.args()
  
Physical reality:
  Function returns 48-byte struct (runtime_data_value)
  
Question:
  How does this 48-byte value move from:
    - Function return location → local variable 'args'?
    
Possibilities:
  A) Via registers (RDX:RAX)? Too large, wouldn't fit
  B) Via stack? Caller sets up out-parameter?
  C) Via RDI register (hidden pointer)? x86-64 ABI?
  D) Other?
```

### C x86-64 Calling Convention (Reference)

```
STANDARD x86-64 ABI:
  - Small return values (≤ 8 bytes): RAX, RDX:RAX
  - Large struct returns (> 16 bytes): Hidden out-parameter via RDI
  
For 48-byte struct:
  - Would use hidden out-parameter approach
  - Caller passes pointer in RDI
  - Callee writes result to that location
  - Caller reads from that location
  
Pattern in generated code:
  CALL __host_args              ; RDI = pointer to output struct
  MOV <local_storage>, RAX      ; or copy from output location
```

### Tier 1 Evidence

**From seed runtime implementation:**

```
The seed runtime:
  - Takes C function pointers
  - Implements x86-64 calling convention
  - Returns C structs via hidden out-parameter
  
This is NOT a choice, it's determined by C ABI.

When Tier 1 compiler generates C code:
  string[] args = std_env_args();  // C code
  
The C compiler then:
  1. Generates hidden out-parameter setup
  2. Calls standard library function
  3. Captures result via out-parameter
```

### Tier 2 Canonical Question

```
Tier 2 compiles directly to x86-64 (no C intermediate).

Two design choices:

Choice A: Follow C x86-64 ABI literally
  ✓ Hidden out-parameter via RDI
  ✓ Caller allocates storage
  ✓ Callee writes via pointer
  ✓ Standard x86-64 convention
  ✓ Interop with C
  
Choice B: Create custom calling convention
  ✓ Potentially more efficient
  ✓ Doesn't need hidden parameter
  ✓ But: needs explicit design
  ✓ And: loses C interop

CANONICAL DECISION: UNKNOWN
```
