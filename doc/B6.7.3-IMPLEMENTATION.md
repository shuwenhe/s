## Problem Analysis

### Root Cause
When analyzing `std.env.args()`, the seed compiler performed:

```
1. Parse: std.env.args as member_expr(member_expr(ident("std"), "env"), "args")
2. Analyze member std.env:
   - object type = "module" (correct, std is SYMBOL_IMPORT)
   - member = "env"
   - → Defaults to TYPE_ANY (no mechanism to look up member type)
3. Analyze member call .args():
   - lhs_type = "any"
   - → Error: "type 'any' has no method 'args'"
```

**Key Insight:** The compiler had no way to determine that `std.env` is a valid module member path.

---

## Solution Design

### Strategy: Leverage Existing Import Signatures Infrastructure

The seed compiler already maintains `import_signatures.meta`:
```
std.env.args|0|0|any      ← Function path with arity/return type
std.io.eprintln|1|*|()
compile.internal.arch.dispatch_init|1|1|string
...
```

**Observation:** If `std.env.args` is in the metadata, then `std.env` must be a module container.

### Two-Part Solution

#### Part 1: Module Member Detection in analyze_expr()
**Location:** `src/cmd/compile/seed/semantic/analyzer.c`, case `AST_MEMBER_EXPR` (~line 870)

When analyzing a member expression where:
- `lhs_type == "module"` (verified via SYMBOL_IMPORT)
- `object` is an `AST_IDENT_EXPR`

```c
// Check if any import signature starts with module.member.
if (strncmp(import_signatures[i].name, "std.env", 7) == 0 &&
    import_signatures[i].name[7] == '.') {
    // std.env.* exists in signatures → std.env is a module member
    *out_type = "module_member";  // Not 'any'!
    return 1;
}
```

**Effect:** `std.env` now returns type `"module_member"` instead of `"any"`

#### Part 2: Import Function Detection in analyze_call_expr()
**Location:** `src/cmd/compile/seed/semantic/analyzer.c`, case `AST_CALL_EXPR` (~line 1269)

When analyzing a method call, before trying type.method lookup:

```c
// Construct complete path from nested member expressions
construct_import_path_into(member, path_buf, sizeof(path_buf));
// path_buf = "std.env.args"

// Check if this exact path or any child exists in signatures
for (i = 0; i < import_signatures_len; i++) {
    if (strncmp(import_signatures[i].name, path_buf, path_len) == 0 &&
        import_signatures[i].name[path_len] == '\0' ||  // Exact match
        import_signatures[i].name[path_len] == '.') {   // Child path
        // Use signature info directly
        *out_type = return_type;
        return 1;
    }
}
```

**Effect:** `std.env.args()` is recognized as a valid import function call

## Implementation Details

### New Helper Function: `construct_import_path_into()`

Recursively builds complete path from nested member expressions:
```c
// Input: AST_MEMBER_EXPR where object=member_expr(...), member="args"
// Output: "std.env.args" in buffer

// Handles arbitrarily deep nesting:
// AST structure: (...(IDENT "std") "env") "args")
// Path result: std.env.args
```

**Algorithm:**
1. Base case: IDENT_EXPR → return name
2. Recursive case: MEMBER_EXPR → recurse(object) + "." + member
3. Return total path length or 0 on buffer overflow

### Integration Points

1. **Import Signature Loading (existing)**
   - `load_import_signatures()` reads import_signatures.meta
   - `resolve_import_signature()` looks up individual entries

2. **Module Root Registration (B6.7.2, existing)**
   - When analyzing USE_DECL (import), extract module root
   - Register "std" as SYMBOL_IMPORT with type="module"

3. **Member Expression Analysis (B6.7.3, new)**
   - NEW: Check if module member appears in import_signatures
   - Returns "module_member" type instead of defaulting to 'any'

4. **Method Call Analysis (B6.7.3, new)**  
   - NEW: Build complete path before checking method exists
   - Check import_signatures for full path
   - Use signature info (arity, return type) if found

## Design Rationale

### Why Module Member Type Detection?
- Without it, `std.env` type remains 'any'
- Method calls on 'any' fail with generic error
- No clear indication that import path is recognized

### Why Complete Path Construction?
- Module member type alone insufficient
- Need to validate entire function call path
- Can reuse existing import_signatures lookup mechanism

### Why import_signatures.meta Over New File?
- Minimal change principle
- Single authority point
- Already proven infrastructure
- Self-contained: one file change, no new files
