```text
Where is CanonicalTypeRef first created, and from which resolved facts?
```

It does not define the final in-memory S structs. It freezes the producer contract that must exist before Layout Authority can be implemented.

## Current production path

The current path keeps enough declaration facts through parsing and import loading, then loses too much type identity before MIR:

```text
Parser
  -> source_file { pkg, items, item_packages }
  -> struct_decl { name, generics, fields }
  -> field/param/signature type strings
Semantic
  -> validates and infers through string bindings
  -> returns diagnostics only
Monomorphization
  -> creates function/method instances with string type args
  -> returns a source_file
MIR lowering
  -> lowers struct declarations to type_expr: "struct"
  -> forwards signature/local type strings
```

Evidence:

| Edge | Evidence | Identity state |
| --- | --- | --- |
| Parser declaration facts | `src/s/parser.s:49-103`, `src/s/ast.s:224-281` | Package, declaration order, struct fields, generics and imported item origins are present. Field and signature types are still spelling strings. |
| Imported item origin | `src/cmd/compile/internal/backend_elf64.s:2548-2556` | Dependency declarations are appended with their original `item_packages` or dependency package. |
| Semantic binding | `src/cmd/compile/internal/semantic.s:11-24`, `src/cmd/compile/internal/semantic.s:262-278`, `src/cmd/compile/internal/semantic.s:701-739` | Function and local bindings are strings normalized through `typesys.parse_type`; `check_source_file` returns `semantic_error[]`, not a typed program. |
| Generic instance tracking | `src/cmd/compile/internal/mono/monomorphization.s:9-23`, `src/cmd/compile/internal/mono/monomorphization.s:73-180` | Generic work/cache keys and generated names are string based. Type argument equality is string equality. |
| Post-mono handoff | `src/cmd/compile/internal/mono/monomorphization.s:191-240`, `src/cmd/compile/internal/backend_elf64.s:2492-2516` | The backend receives a monomorphized `source_file`; no type registry crosses the handoff. |
| Lowering loss | `src/cmd/compile/internal/ir/lower.s:16-50`, `src/cmd/compile/internal/ir/lower.s:217-255` | Struct declarations lose fields at `type_expr: "struct"`; function parameters, returns and locals remain type strings. |

Therefore the proposed producer belongs after import loading, while semantic resolution can still access source declarations and establish scopes and substitutions. The current checker does not yet produce these resolved facts as a persistent result. Introducing identity after the demonstrated lowering loss would require an earlier retained declaration table; MIR strings alone are insufficient.

### Exact integration seam and coverage limits

In `load_source_graph` (`backend_elf64.s:2492-2516`), the checked route is:

```text
append_dependency_items(combined, combined.uses, visited)
    -> semantic.check_source_file(combined, source)
    -> mono.monomorphize_file(combined)
```

The semantic call is the integration seam to replace or extend with a typed result. Within that semantic operation, the first successful resolution of each type must produce its canonical reference; merely allocating ids after diagnostics have been returned does not establish resolution. `semantic.s:262-278` currently returns diagnostics only, and `make_function_binding` at `semantic.s:716-739` normalizes spelling without binding it to a canonical declaration. There is no existing `CanonicalTypeRef` producer at this seam.

Three evidence limits are part of the contract:

- `append_source_items` preserves package spelling and declaration payloads, but does not attach each dependency's `uses` or resolved source path to its items. Semantic collects import roots from `file.uses`. A package label is useful provenance, but this does not prove that complete per-source resolution scope or unique package identity is already preserved. The future producer must receive that context explicitly.
- `monomorphize_file` filters and appends `file.items` at `mono/monomorphization.s:236-252` without corresponding `item_packages` updates. Consequently a post-mono array position cannot be assumed to identify the original declaration or its package. Declaration references assigned before mono must survive item movement and specialization.
- `should_skip_semantic_check` at `backend_elf64.s:2572-2577` skips both semantic and mono for selected compiler paths; `load_source_graph` returns `combined` on that branch. The build path subsequently calls `lower_main_to_mir` at line 298. Freezing the contract does not establish enforcement on those paths. Any future claim of canonical pipeline coverage must account for these entries explicitly.

## Producer boundary

The producer boundary is:

```text
source_file + package origins + scope + generic substitution
    -> semantic type resolution
    -> TypeRegistry intern
    -> CanonicalTypeRef
```

This boundary belongs to semantic resolution, with ownership of the registry at the compilation/package-graph level. Semantic may expose it as a new result next to diagnostics, for example conceptually:

```text
check_source_file_typed(source_file, source, TypeRegistry)
    -> SemanticResult {
        diagnostics
        typed_source
        type_registry
    }
```

The concrete function name is open. The contract is not open: the first successful resolution of a type spelling must intern and return an opaque semantic identity, not another canonical string.

## Required producer inputs; representation deferred to 1.3d

The following are semantic requirements on the boundary. They do not freeze registry storage, constructor signatures, a declaration-key encoding, or the concrete owner object; those decisions belong to 1.3d.

### 1. Declaration identity

A named declaration is identified by package origin plus declaration identity inside that package graph.

The producer needs the resolved package and selected declaration, including its generic binders and field declarations. Whether 1.3d represents this with a symbol id or an immutable declaration-table entry remains open. A mutable AST item position is insufficient: mono already changes those positions. Package spelling alone is not proof of resolved package identity.

Invariant:

```text
demo.a.Foo != demo.b.Foo
```

even if both print as `Foo`.

### 2. Structural components

Constructed types require their semantic constructor kind and resolved child references. Identity-relevant qualifiers, component order, array length and generic arguments must be retained where the language supports them. The exact constructor API belongs to 1.3d. For example, array length must be a resolved semantic value, not the original token text.

Display strings may be cached for diagnostics and artifact text, but they are not identity.

### 3. Generic identity

Generic identity is resolved at substitution time:

```text
Box<T> + int
    -> named_instance(Box declaration key, [int ref])
```

Semantic resolution must bind the generic declaration and its parameters before mono. If all arguments are concrete there, it can request the concrete identity immediately. If substitution becomes concrete during mono, mono must request that identity through the same semantic construction authority using existing references and substitutions, before the instance crosses into lowering. This is construction of a new concrete type, not repeated source resolution. The current mono code tracks function/method specializations; it does not establish a canonical `Box<int>` struct type producer. Names such as `identity__mono_int` are code generation names only.

Required behavior:

```text
canonicalize(Box<int>) == canonicalize(Box<int>)
canonicalize(Box<int>) != canonicalize(Box<string>)
canonicalize(pkg.a.Box<int>) != canonicalize(pkg.b.Box<int>)
```

### 4. Ownership

The required lifetime spans the compilation/package graph. Selection of the concrete owning context and storage model belongs to 1.3d.

Semantic resolution is responsible for establishing the inputs to identity creation:

```text
package origin
visible declarations
generic parameter bindings
resolved field and signature types
constant array lengths
diagnostic source positions
```

Monomorphization may request new concrete named instances through the same registry, but it must not rebuild identity by reparsing generated strings. MIR and SSA carry handles or side table indexes owned by the same registry.

### 5. Propagation

After resolution, stage handoffs carry `CanonicalTypeRef`:

```text
typed source/signatures/fields/exprs
  -> monomorphized typed source
  -> MIR locals/operands/calls
  -> SSA values/phis
  -> Layout/ABI queries
```

String fields may remain temporarily for dumps, compatibility and diagnostics, but they become derived metadata. A downstream pass that receives only `"Box<int>"` does not have enough authority to recover identity.

This is the required handoff, not the current implementation. A migration path that still reparses semantic type strings must remain marked as legacy and cannot count as satisfying the invariant. Missing or unresolved identity must produce an explicit diagnostic at the canonical handoff; it must not silently fall back to spelling.

### 6. Stability

Within one compilation:

```text
canonicalize(T) repeated in the same registry returns the same CanonicalTypeRef.
CanonicalTypeRef equality is handle equality.
```

Across compilations, raw integer ids are not stable unless an explicit serialization format is added. Persistent identity, if needed later, should serialize semantic keys such as package identity, declaration key and constructor graph.

## Post-resolution type identity invariant

```text
Once a source type has completed canonical resolution,
no production stage may recover semantic type identity
by reparsing type spelling.
```

Allowed:

```text
source syntax -> resolve once -> CanonicalTypeRef -> registry lookup
```

Disallowed:

```text
CanonicalTypeRef -> string -> parse_type_ref -> new identity
```

Disallowed:

```text
MIR/SSA type_name string -> parse -> infer package declaration
```

This is the producer-side companion to the 1.3b layout query contract:

```text
CanonicalTypeRef + TargetDataLayout
    -> layout_of()
    -> TypeLayout
```
