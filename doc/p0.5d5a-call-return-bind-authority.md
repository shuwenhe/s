## Why Existing Code Does Not Establish A Routing Gap

### AST preservation is not executable lowering

`from_syntax_checked` -> `from_syntax` -> `convert_stmt/convert_expr` retains more
information than the selected-function MIR path. The known caller in the frozen
closure is `tests/test_pipeline_regression.s:50`, which checks AST-like features.
The normal build path calls `lower_main_to_mir` instead. No full executable
consumer of those `ir_ast.call_expr`/let/return nodes was established.
`convert_expr` also writes `<expr-callee>` for non-name callees and uses symbolic
calls such as `if_expr`; the representation cannot be presumed fully resolved.
Switching build to this conversion alone is not an established fix.

### The actual MIR edge still loses the call

`ir/lower.s:683` serializes a let statement as `"let " + name`.
`make_entry_block_with_condition:1003` stores that in `eval(op="line")`.
`mir.s:894` traverses calls only for ownership/reference observations.
The MIR enum has generic assign/eval operations, so absence of a named `Call`
variant alone would not prove a gap. The stronger evidence is that this producer
does not emit a call/result-binding operation, and the inspected MIR interpreter
at `backend_elf64.s:3260` only extracts prints from eval text.

`mir_terminator` has a kind, condition and edges, not a dedicated return-value
field; no equivalent carried return result for this probe was found in this
producer/consumer route. A generic `assign` struct or local-slot declaration
does not supply the missing value flow by itself.

### SSA call counts are not SSA call instructions

`ssa_core.s:293` adds graph counts/debug lines to a text-driven pipeline;
`build_dataflow_model` counts `" call="`. `analyze_instruction_ssa:474` produces
summaries, and `build_instruction_value_graph:722` constructs sample edges from
counts. None supplies this call's target, argument operands and result definition.
Additionally, `backend_elf64.s:310` calls the unqualified spelling
`build_ssa_pipeline_with_graph_hints_and_margin`; repository search found uses
but no declaration with that exact spelling. The similarly named `ssa_core`
function is not proof that the unqualified call resolves. This remains an
independent binding uncertainty, not a reason to add an alias during this audit.

### Interpretation has value flow but is not its compiled representation

`backend_elf64.compile_writes/compile_exit_code` -> `execute_source_main` ->
`execute_block_in_place` -> `execute_stmt` -> `eval_expr` -> `eval_call` is a
source-backed execution path. `eval_call` evaluates arguments, consults
`resolved_callee`, and invokes source function bodies. `execute_stmt` binds
computed values and records return control values. These are real implementations
of interpreter behavior, but they emit no reusable executable call IR.
The producer would itself need to translate this interpreter if it were part
of Stage1. It cannot stand in for that translation. Qualified member/intrinsic
support for this exact probe is not proven by generic interpreter branches.

### A separate producer/consumer chain exists only in the seed

The C seed contains `AST_CALL_EXPR -> ARG + CALL temp`, `AST_RETURN_STMT -> RET`,
and `AST_LET_STMT -> MOV local,temp`. The SSEED serializer writes those records.
The standalone consumer loads ARG values, emits a call, stores `%rax` to the
result slot and handles RET; the hosted runtime similarly writes `callee_ret`
with `values_set`. This establishes code-level consumer mechanisms, not support
for every ABI/target or execution of the frozen probe. It does not qualify C seed
semantics as canonical production authority.
