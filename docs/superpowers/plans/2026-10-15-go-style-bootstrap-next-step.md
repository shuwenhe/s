# Go 风格自举：恢复 P2.1 的实施步骤

本轮目标：依据用户最新的自举实现请求，先解除已复现的 `T[]()` 阻塞，再执行原 P2.1 测试。不能把这一步称为完整自举。

参照本地 Go：`src/cmd/dist/buildtool.go` 的 `bootstrapBuildTools` 用已有工具链构建第一轮；`src/cmd/dist/build.go` 的 toolchain2/toolchain3 使用新编译器连续重建同一套工具源码。S 的阶段驱动应在真实编译器生产链可执行后接入。

## 实施边界

- 保留 S 的 `T[N]` / `T[]` 语法；本轮只处理 `T[]()`。
- 不引入 vec 类型，不采用来源解释执行得到的常量冒充机器码。
- 复用 Seed 已有静态类型字符串和运行时数组容器，不把尚未验收的第六版草案整体变为语言规范。
- 构造经 Semantic 解析后携带规范 `T[]` 类型；Seed 的显式 IR 记录采用 `ARRAY_NEW|result|T[]|0`，Hosted 与 Standalone 各自消费该操作。
- 检查构造参数、未知类型、数组元素写入、函数参数及返回类型；保留普通调用目标检查。
- 保持现有数组的复制、增长和错误语义；新的 Move/panic/固定数组契约仍需单独完成设计，不在此步骤臆定。
- P1、Stage0、正式 compiler main 和 bootstrap 分派不变。

## 任务与证据

- [ ] RED：原 P2.1 失败已复现；新增独立构造/类型/运行测试，并运行得到相同 Semantic RED。
- [ ] GREEN：只将空索引且元素可解析为类型的调用识别为数组构造；普通 `a[i]()` 仍按普通调用检查。
- [ ] GREEN：发射携带 `T[]` 的 ARRAY_NEW；两种消费路径验证零长度记录并构造各自的空数组。
- [ ] 验证：正例、负例、Hosted 与 Standalone、现有 Seed 回归、原 P1/P2.1 测试。
- [ ] 记录：通过项目和首个剩余失败；若新失败是执行器缺口，保留它并分析原因，不跳过断言。

## 判定

动态数组构造通过不代表全面类型化 IR、完整 SSA 或自举成功。P2.1 必须执行验证器正负例后才能报告行为验证结果。完整 Canonical Stage1、Stage2、Stage3 及固定点仍需实际编译和产物证据。
